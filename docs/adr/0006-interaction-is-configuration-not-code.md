# 互動審查用設定描述，並自己寫一個極小的 CDP 用戶端

視覺審查改為全程走 Chrome DevTools Protocol：一個 headless Chrome 實例跑完
所有畫面，每個畫面可以帶一串「動作」——點、輸入、捲動、等待、拍照。
動作寫在 `.claude/review/config.json` 裡，是資料不是程式，使用者不必寫任何程式碼。

原本的一次性 `chrome --headless --screenshot` 被整個移除。

## 為什麼需要互動

這個工具最初的需求就是「視覺與**互動**審查」。第一次真實審查時，審查者也把
「沒有 click、輸入、提交、導覽」列為 blocking 級的需求偏離。靜態截圖抓不到
「點下去沒反應」「面板展開後版面壞掉」這一類問題，而那正是使用者
反覆手動檢查的原因。

## 為什麼自己寫 WebSocket 用戶端

CDP 只能走 WebSocket，而 Python 標準函式庫沒有 WebSocket。三條路：

| 作法 | 代價 |
|---|---|
| `pip install websockets` | 破壞「每個專案零設定就能用」，而且綁定某一個 Python 安裝 |
| 改用 Node（開發機已有 v24 與一份現成的 CDP 驅動） | 違反「全部 Python」的決定，工具鏈變兩種語言 |
| **自己寫用戶端需要的那一小塊 RFC 6455** | 約 130 行協定程式碼要自己維護 |

選第三條。對本機 CDP 來說範圍很窄：握手、送遮罩過的文字訊框、
收可能很大又可能分段的訊框（截圖回來是好幾 MB 的 base64，
所以 64 位元長度與延續訊框必須處理）。已用真實 Chrome 驗證：
點擊前看不到的文字點擊後出現，整趟 2.8 秒。

## 順帶解決的兩件事

- **一個 Chrome 跑完所有畫面**，比原本每張圖開兩次行程（截圖一次、
  `--dump-dom` 一次）更快。
- **截圖與 DOM 文字來自同一次渲染**。原本分兩次載入，兩次的畫面不保證一樣，
  而 ADR-0003 的截斷偵測正是靠這兩者對照。

## 一個環境陷阱

Chrome 的 `--user-data-dir` 刻意放在系統暫存目錄，不放在專案的 `.claude` 底下：
開發機上既有的 `stop-hook.ps1` 會殺掉指令列同時含 `--headless` 與 `claude` 的
Chrome 行程，放在 `.claude` 底下會被它掃到而在審查中途被殺。
