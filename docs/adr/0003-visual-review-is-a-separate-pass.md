# 視覺審查與程式碼審查是兩個獨立的審查

一個回合會產生兩個互不相干的背景審查：視覺審查（截圖＋DOM 文字）與程式碼審查（diff）。
各自的材料包、各自的 schema、各自的報告、各自喚醒執行者一次。

理由是實測的耗時差了一個數量級：

| 審查 | 實測 |
|---|---|
| 視覺（單張截圖） | 14.3 秒、21.7 秒 |
| 程式碼（3.4 KB 材料包） | 152.7 秒、652.3 秒 |

使用者最痛的是 GUI 要自己反覆看、反覆截圖。把 20 秒就能回來的東西
排在可能要 11 分鐘的東西後面，等於把最有價值的部分作廢。

## Consequences

- 一個回合會被喚醒兩次，使用者會看到兩份報告。這是刻意的。
- 視覺審查抓不到「這行 CSS 改動導致畫面變醜」這種跨兩份材料的因果，
  因為它看不到 diff。接受這個缺口。

## 已知的能力邊界（實測，不是推測）

同一張刻意植入兩個缺陷的截圖，測了兩次（一般提示與逐項檢查清單）：

- **對比度過低到難以閱讀**：兩次都抓到。
- **文字在容器邊緣被截斷**：兩次都沒抓到。第二次它看到了那個容器、
  注意到文字緊貼邊框，但明確寫下「目前未見文字被切掉」。

分界線是**這個資訊在圖片裡存不存在**。對比度是圖片本身的性質；
截斷則需要知道「本來還有字」，光看圖無從得知——它的判斷其實是誠實的。

因此材料包除了截圖，還要附上該畫面的 DOM 文字（`chrome --headless --dump-dom`），
讓「DOM 裡有這些字」與「畫面上只看得到這些」可以對照。
上一回合的基準圖則補另一半。
