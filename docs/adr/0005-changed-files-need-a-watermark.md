# 「這一輪改了什麼」需要修改時間水位線，不能只用 git status

判斷一個回合改了哪些檔案時，`git status --porcelain` 的結果必須再與
「修改時間晚於上一次派工時刻」取交集。不可以直接採用 git status。

理由是這個工具第一次真實審查自己的程式碼時，審查者交回的 blocking 級發現：

> git_changed_files() 每次都回傳整個 working tree 的所有未提交程式碼檔案，
> hook 沒有依回合或游標過濾 git 清單；第一輪送審後只要檔案仍未提交，
> 下一次 Stop 就會再次建立工作單並攔阻，Claude 會反覆審同一批檔案而無法正常收尾。

這是對的。`git status` 回答的是「相對於 HEAD 有什麼不一樣」，不是
「相對於上一個回合有什麼不一樣」。使用者不會每一輪都 commit，所以在
git 專案裡，少了水位線就是一個保證發生的無窮攔阻迴圈。

水位線在 hook 派工的當下就定住，寫進 state 與工作單，背景審查沿用同一個值。

## 水位線只能過濾，不能發現

寫這條 ADR 時我原本聲稱水位線「順便補上了 Bash 改檔的盲點」。**那是錯的**，
而且第一次在真實 session 裡試跑就被打臉：使用者叫 Claude 在一個檔案加一行註解，Claude 用 Bash 做的，而那個專案不是 git repo。結果是——

- `git status` → 沒有（非 git repo）
- 工具呼叫紀錄的 `file_path` → 沒有（Bash 沒有這個欄位）
- **候選清單是空的，hook 認為這一輪什麼都沒改，靜默放行**

水位線是拿來**過濾**候選清單的，它不會**產生**候選。所以另外加了第三個來源：
直接走一遍專案目錄，找出修改時間晚於水位線的程式碼檔。這才是唯一可靠的發現機制，
git status 與工具呼叫紀錄退成線索。

走一遍目錄的成本實測（就地修剪 `node_modules`、`.git`、`.venv` 等與所有點開頭目錄）：

| 專案 | 掃過的項目 | 耗時 |
|---|---|---|
| 大型專案（React 前端＋Python 後端，含建置產物） | 6,377 | 165 ms |
| 中型專案（Python 桌面工具） | 350 | 13 ms |
| 中型專案（React 前端＋FastAPI 後端） | 308 | 5 ms |

相對於 Python 啟動本身的 113 ms，這個代價可以接受。

## 水位線的起始值

session 的第一輪沒有前一個水位線可用。起始值取 **transcript 檔的建立時間**，
也就是這個 session 開始的時刻——比它新的改動就是這個 session 的工作。
不能用 0：那會把整個專案的所有程式碼檔都當成本回合改動。

## Consequences

- mtime 不可靠時會失準：檔案被還原成舊內容但 mtime 更新了會誤報，
  某些同步工具或 checkout 也會整批更新 mtime。誤報的方向是「多審一次」，
  可以接受；漏審才是不能接受的方向。
- ~~點開頭的目錄一律跳過，所以 `.github` 底下的 CI 設定不會被審。~~
  **已修正。**這個「取捨」撐不住審查者的質疑：CI 設定改壞的後果通常比
  一般程式碼更嚴重，用「順便避開 `.git` 與 `.venv`」當理由把它排除掉並不划算。
  改成白名單：`.github`、`.gitlab`、`.circleci`、`.azure`、`.devcontainer`、
  `.vscode` 會被審，其餘點開頭目錄（含 `.claude` 自己的產物）仍然排除。
- 原本的測試全部使用非 git 專案且都透過 Edit/Write，所以同時漏掉了
  git 反覆攔阻與 Bash 改檔兩條路徑。兩者都已補上回歸測試。
