# 審查在背景跑，由 harness 喚醒執行者，而不是讓使用者等

審查不在 Stop hook 裡同步執行。執行者在收尾前把審查丟成 Claude Code 的背景任務，
照常回覆使用者；審查完成時 harness 會自動重新喚起執行者並交付報告，
不必等使用者發下一句話。Stop hook 退化成一個瞬間完成的本地檢查：
「這回合改了程式碼卻沒有送審 → 攔阻，要求補送」——hook 本身完全不呼叫審查者。

理由是實測數字。同一份 3.4 KB 的材料包審兩次：

| 設定 | 耗時 | tokens |
|---|---|---|
| 預設（載入全部 MCP server 與 plugin） | 152.7 秒 | 36,270 |
| 關掉 MCP server 與 plugin | 652.3 秒 | 24,047 |

用更少的 token 花了 4.3 倍的時間。耗時不是被 context 決定的，是伺服器端的變異，
而且不受我們控制（`gpt-5.6-luna`、high reasoning、priority tier）。只有兩個樣本，
不足以宣稱分布，但足以推翻「同步等待」：任何逾時上限若設在 90 秒，兩次實測都會逾時，
使用者白等 90 秒又拿不到審查；若不設上限，一次對話可能卡 11 分鐘。

背景任務同時解掉了另一個問題：Claude Code 的背景任務結束時會自動重新喚起 session，
所以審查結果不必等使用者發話就能送達執行者。「即時」與「不等待」原本看似衝突，
在這個機制下同時成立。

## Consequences

- 攔阻（Block）的意思改變了。Stop hook 不再因為審查發現而攔阻，
  而是因為「該送審卻沒送審」而攔阻。審查發現改由背景任務的喚醒送達。
- 執行者可能會多走一小段錯誤方向，直到審查結果回來。這是為了不讓使用者等而付的代價。
- 這套機制依賴 Claude Code 的背景任務會重新喚起 session。這一點必須在實作第一步實測驗證，
  失敗時退回「結果寫檔、下一輪注入」。
