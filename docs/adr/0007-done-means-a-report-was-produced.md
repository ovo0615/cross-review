# `.done` 的語意是「產出了報告」，不是「全部都審過了」

背景審查結束時寫 `.done`，代表它**產出了一份誠實的報告**。
報告本身會揭露自己有多完整。`.done` 不代表所有畫面都拍到、
所有檔案都收錄、或審查毫無缺口。

具體來說，視覺審查若有部分畫面截圖失敗、但仍有其他畫面成功，
它會產出報告、在報告開頭列出哪些畫面失敗與原因，然後寫 `.done`。
Stop hook 不會因此再多喊一次「審查沒跑完」。

## 為什麼

審查者在連續四個回合把這件事列為 major 級發現，主張
「部分失敗仍寫 `.done` 會讓 hook 把不完整的審查當成成功完成」。
這個顧慮成立，但兩種語意各有道理，這裡記錄選擇與理由：

| 語意 | 行為 | 代價 |
|---|---|---|
| **「產出了報告」**（採用） | 部分失敗照樣出報告並標示不完整 | hook 不會額外提醒 |
| 「全部都審過了」 | 任何畫面沒拍到就不寫 `.done` | 在一份已經誠實揭露的報告上再疊一句警告 |

採用前者，因為 hook 的「沒跑完會出聲」機制存在的目的是**抓沒有報告的情況**
——審查程序崩潰、被中斷、根本沒被啟動。那些情況使用者什麼都看不到，
所以必須有人喊。而部分失敗時報告是存在的，而且第一段就寫著哪些畫面沒拍成。
再讓 hook 喊一次，只是在使用者已經讀到的資訊上疊一句重複的警告，
久了會讓那個警告失去意義——真正該注意的「完全沒有報告」反而被稀釋。

換句話說：**揭露的責任在報告，喊叫的責任在 hook，兩者不該重疊。**

## 這條規則的邊界

「產出了報告」不等於「跑完就算數」。以下情況仍然**不寫** `.done`：

- Codex 找不到、逾時、輸出非法或缺欄位（`run_codex` 回傳錯誤）
- 一個畫面都沒拍到，而且失敗原因是錯誤而非「dev server 沒開」
- `max_images` 小到放不下任何一個畫面
- 未預期的例外

這些的共同點是**沒有報告，或報告裡沒有任何實質內容**。
使用者看不到東西的時候，hook 必須出聲。
