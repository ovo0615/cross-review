# 審查者讀的是觀察來的事實，不是執行者的自述

材料包的內容一律來自客觀紀錄——Claude Code 自己寫的 transcript（harness 記錄的每一次工具呼叫），
有 git 的專案再附 `git diff`——而不是讓執行者自己總結「我這輪做了什麼」交給審查者。

理由：讓執行者組裝審查者的輸入，等於讓被審查的一方決定審查的範圍。這不需要惡意，
一個模型自然會挑對自己有利的敘述來講。獨立性是這套工具唯一的價值來源，
一旦讓執行者代筆，審查就退化成自我確認。

代價是實作變麻煩：要解析 JSONL、要記住「上次讀到哪一行」、要在 git 與非 git 專案走兩條路。
這個代價是刻意付的。

## Considered Options

- **執行者自述改了什麼**——最簡單，被否決，理由如上。
- **一律 git，非 git 專案自動 `git init`**——最精準，被否決：開發機上 45 個專案有 21 個不是 git repo，
  其中數個資料夾放模擬輸出（數百 MB 的二進位檔），沒有事先寫好 `.gitignore` 就 `git add` 會全部拖進去。
- **檔案系統快照比對**——不依賴 git 也不依賴 transcript，被否決：等於重造一套 `.gitignore` 與
  大檔規則，而且每個回合都要走一遍整個專案目錄。
