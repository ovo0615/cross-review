# ADR-0008：送不送審由使用者決定，門檻只負責「不會漏」

日期：2026-09-02
狀態：**部分被 ADR-0010 取代**（預設值那一段不再適用）

> **2026-09-02 補記**：工具改成全域安裝之後，本文選擇 `threshold` 當預設的
> 前提（逐專案安裝＝安裝那一刻已經表態）不成立了。預設已改為 `manual`，
> 而且「同意送出」改為記在使用者層級、專案設定只能收緊——見 ADR-0010。
> 本文其餘部分（三種模式的定義、門檻只保證不漏、不送審的回合什麼都不推進）
> 仍然有效。

## 背景

原本只要有程式碼改動就一定攔阻送審。用量帳本顯示每次審查約 **11 萬 tokens、
170～650 秒**。實際使用下來，大量回合是改一兩行、換個字串、調個設定——
這些回合的審查幾乎不產生價值，成本卻跟大改動一樣。

同期做的 diff-only 最佳化把材料包壓了 21%。相比之下，「四分之三的回合根本不審」
是 75%。**觸發時機才是成本的主要槓桿，材料包大小是次要的。**

## 決定

觸發模式由專案設定 `trigger` 決定，共三種：

- `auto`：有改動就攔阻。交付前的收尾用。
- `manual`：永不自動送審，每輪只報累積量。
- `threshold`（**預設**）：平常同 manual，累積超過 `auto_when_files`（10）
  或 `auto_when_diff_bytes`（20 KB）時自動送一次。

預設是 `threshold` 而不是 `manual`。純手動有一個很具體的失效方式：**會忘記**，
而「忘記送審」跟「審過了沒問題」在畫面上長得一模一樣——這是斷路器暫停時
必須每輪出聲的同一條理由。

沒有送審的每一輪都印一行累積量。一行的噪音，換「不會靜默漏掉」。

## 明確不做的事

**不依副檔名或改動行數判斷「這次重不重要」。** 改一行 `config.json` 可能比改
三百行測試更危險，行數跟風險沒有關係。那種猜測會在最需要審查的時候放行。
門檻只用來保證不會漏，不用來判斷值不值得——值不值得由使用者決定。

## 後果

- **不送審的回合什麼都不能推進。** 水位線、逐字稿游標、`head_sha`、
  `reported_deletions` 全部維持原樣，否則那批改動下一輪就消失了。
  累積清單每輪重算（實測 165 ms）。
- **手動觸發的審查不寫 `state.json`。** hook 也在寫那個檔案，兩個行程各自寫
  會互相覆蓋。改成寫一張收據 `reviewed.json`，由 hook 在下一次 Stop 兌現。
  單一寫入者仍然是 hook。這是 `breaker.json` 當初必須拆檔的同一個理由。
- 回合編號改成掃描已存在的工作單再加一，否則手動與自動會撞號。
