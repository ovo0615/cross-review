# ADR-0009：斷路器的狀態是「只追加的事件記錄」，不是一份狀態檔

日期：2026-09-02
狀態：已採用

## 背景

斷路器的狀態檔被拆過四次，每一次都是為了修「剛剛發現的那一種交錯」：

1. 全部放 `state.json` —— hook 與背景審查互相覆蓋。
2. 拆出 `breaker.json` —— 但背景審查自己就有兩個行程（程式碼與視覺併行），
   仍然互相覆蓋。實測重現：code 記下額度暫停後，visual 用更早的快照寫回，
   暫停消失。
3. 拆成 `breaker.<模式>.json` —— 但額度暫停還共用一個檔。兩個模式解析到的
   恢復時間不一定相同（一邊拿到 `try again at 1:27 PM`，另一邊只能用兜底的
   一小時），後寫的會把期限縮短。
4. 寫入前重讀並取最大值 —— 額度暫停保住了，但「舊的成功」仍會抹掉
   「它讀完之後才出現的失敗」。補了那個之後，三個行程交錯時
   `max(0, 目前 - 讀到的)` 又會把新的失敗算成 0。

每一次補丁都更複雜，而且下一種交錯永遠還在後面。

## 決定

根因不是某一個順序，是**無鎖的「讀出 → 修改 → 整份寫回」**。所以拿掉這個動作：

- 每次事件只**追加一行** JSONL 到 `breaker.<模式>.log`。追加是原子的，
  而且不需要先讀既有內容。
- 狀態一律**用讀的推導**：連續失敗數是「最後一次成功之後的失敗行數」，
  模式暫停是「失敗數達門檻時，從最後一次失敗算起冷卻」，
  帳號層級的暫停是所有事件的最大值。
- 連續失敗造成的暫停**不存**。存起來就又需要合併，又回到原點。

交錯於是不再是需要窮舉的東西。

## 後果

- **不需要檔案鎖。** 用 8 個行程同時寫入驗證過：8 筆全在、每一行都完整。
- 伺服器明講的恢復時間要**優先於**兜底值，不能只取最大值——否則另一個模式
  的兜底一小時會把 13:27 拉長成 14:25。不會提前重試（安全），但白等一小時。
  所以事件裡多存一個 `account_exact`。
- 舊的兩代狀態檔（`breaker.json`、`breaker.<模式>.json`）改為**只讀的遷移來源**，
  升級的專案不會突然失去還有效的暫停。
- 記錄會一直長大。一次審查一行、一行約 200 位元組，一千次審查約 200 KB，
  讀取成本遠低於 hook 本來就要做的目錄掃描（44～165 ms）。刻意**不做裁剪**：
  裁剪本身就是讀改寫回，會把剛剛拿掉的那個問題請回來。
