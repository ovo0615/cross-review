# 在真實專案上的驗證

以下測試在一個**真實的 React + Vite 前端專案**（約 6,400 個檔案、
19 個 `.tsx` 原始檔合計 822 KB）上執行。為了不動到工作副本，
測試跑在該 repo 的一個 `git worktree` 上，另起一個 dev server，
測完把 worktree 移除。

審查者：`gpt-5.6-luna`，`reasoning effort=high`。

## 結果

| | 測什麼 | 結果 |
|---|---|---|
| T1 | dev server 沒開時的行為 | ✅ 產出報告檔說明「一個畫面都沒拍到」與原因，寫 `.done`，**完全沒有呼叫審查者**（零成本） |
| T2 | 首次擷取、建立基準圖 | ✅ 3 個畫面，118 秒。**並抓到產品裡的真問題**（見下） |
| T3 | 無效的測試設定 | ✅ 工具正確回報「沒有改變」——因為當時的 CSS 選擇器沒對到任何元素，畫面確實沒變 |
| T4 | 真實的視覺回歸 | ✅ 抓到，並**引用 DOM 對照當證據**、**明確區分是新回歸而非既有問題**。66 秒 |
| T5 | 程式碼審查含真實 `git diff` | ✅ 材料包有完整的 unified diff；審查者指出截斷沒有省略號、選擇器對 DOM 結構脆弱、以及測試用程式碼混進產品 CSS。70 秒 |
| T6 | 安全邊界（`.claude/review` 指向專案外） | ✅ 三層都擋住：判定不安全、`log_error` 不寫到外面、背景審查以結束碼 2 拒絕執行 |
| T7 | `max_bytes` 是不是硬上限 | ⚠️ **抓到一個真的 bug**（見下），修正後全部在上限內 |
| T8 | 還原回歸後會不會誤報 | ✅ 沒有誤報。正確識別「相較基準已恢復完整文字」是改善而非缺陷 |

## T2 抓到的產品問題

第一次擷取基準圖時，審查者就在**實際畫面上**抓到兩處：

> 中文狀態列使用 U+00B7 半形中點作分隔，不符合中文內文標點全形規範

這條規範來自專案的 `CLAUDE.md`。工具把規範檔放進材料包，
審查者於是拿它去對照渲染出來的畫面——這是純靜態分析做不到的檢查。

## T4 的回歸偵測長什麼樣

刻意讓功能卡的說明文字被容器切掉（`max-width` + `overflow: hidden`），
審查者回報：

> DOM 中的完整說明未完整顯示，例如「Stackup」只看到「Sta」、
> 「Port」只看到「Por」，多張卡片均在句中被截斷；
> **基準圖可完整顯示相同文字。**

三件事同時成立：抓到截斷、用 DOM 對照當證據、
並且把它跟基準圖區分開來——這才是「你這次弄壞的」而不是「本來就壞的」。

## T7 抓到的 bug

把 `max_bytes` 設成 500，產出的材料包是 **200,000 位元組**——也就是預設值。

原因是設定值驗證對「低於下限」的處理是**退回預設**，
而 `max_bytes` 的預設遠大於下限。**使用者要求更小，卻拿到大 400 倍的東西。**

靜默給出比要求更大的值，永遠比給出更小的危險。已改成：

- 根本不是數字 → 用預設
- 負數或零 → 用預設（顯然是打錯）
- 正數但低於下限 → **夾到下限**

修正後的實測：

| 設定 | 實際上限 | 產出 |
|---|---|---|
| 200,000 | 200,000 | 200,000 |
| 50,000 | 50,000 | 50,000 |
| 10,000 | 10,000 | 10,000 |
| 2,000 | 2,000 | 1,998 |
| 500 | 1,000（夾到下限） | 1,000 |

## 一個測試方法上的教訓

T3 原本被記為「工具沒抓到回歸」。實際比對截圖的雜湊之後才發現
**畫面根本沒變**——注入的 CSS 選擇器沒有對到任何元素，
而且即使對到了，那些說明文字本來就只佔一行，`white-space: nowrap` 是 no-op。

工具的回報從頭到尾都是正確的。

之後的測試改成**先驗證像素真的變了，才呼叫審查者**。
測試失敗時第一個要懷疑的是測試本身。
